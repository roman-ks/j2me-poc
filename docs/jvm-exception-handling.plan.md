# JVM Exception Handling Plan

This plan covers Java exception propagation and catch handling for the embedded
JVM runtime in `/home/roman/projects/j2me-poc/tools/jvm-poc`. The goal is real
CLDC-compatible behavior for games while keeping the happy path cheap on ESP32.

## Goals

- Support Java `throw`, `catch`, and `finally` bytecode patterns generated by
  the current Maven/JDK setup (`-source 1.3 -target 1.3`).
- Keep normal non-exception execution near zero overhead.
- Avoid C++ exceptions for Java exceptions.
- Make exception ownership correct with the cooperative Java thread scheduler.
- Add tests that compile Java classes and verify runtime output through the
  existing C++ JVM test harness.

## Non-Goals For First Pass

- Java stack traces.
- `Throwable.fillInStackTrace()`.
- cause/suppressed exception chains.
- fully detailed exception messages for VM-generated exceptions.
- `jsr` / `ret` support unless a real class requires it.

The current compiler emits duplicated `finally` cleanup plus catch-all exception
table entries, not `jsr` / `ret`, for a simple Java 1.3 `finally` probe.

## Current Gaps

- `class_file.cpp` parses `Code` but skips the exception table:

```cpp
uint16_t exceptionTableLength = code.u2();
code.skip(static_cast<size_t>(exceptionTableLength) * 8);
```

- Interpreter has no `athrow` implementation.
- Runtime has no Java exception propagation state.
- Java boot classes do not yet include a throwable hierarchy.
- There is no `ExecutionTrace` surface for uncaught exceptions or thread death.

## Class File Representation

Add a compact exception handler record to `MethodInfo`:

```cpp
struct MethodInfo {
    struct ExceptionHandler {
        uint16_t startPc = 0;
        uint16_t endPc = 0;
        uint16_t handlerPc = 0;
        uint16_t catchType = 0; // constant-pool Class index; 0 means catch-all/finally
        std::string catchClass; // resolved once during parse; empty when catchType == 0
    };

    std::vector<ExceptionHandler> exceptionHandlers;
};
```

Parsing should resolve `catchType` to class name immediately. Handler tables are
small in CLDC/game code, so a `std::vector` and linear scan on throw are fine.

## Runtime State

Use explicit interpreter state, not C++ unwinding.

```cpp
struct Runtime {
    Value pendingException; // active task scratch only
};

struct ThreadTask {
    std::optional<RuntimeFrame> suspendedFrame;
    Value pendingException; // persisted owner state for this cooperative task
    bool finished = false;
};
```

If `Value` does not have a cheap empty/null state suitable for this, add a small
`std::optional<Value>` or a dedicated `ExceptionState` wrapper. Prefer avoiding
heap allocation in the state holder itself.

### Thread Ownership Rule

Only one Java task executes at a time, so no locks or maps are needed. At
scheduler boundaries:

```cpp
rt.currentTask = &task;
rt.pendingException = task.pendingException;
task.pendingException = {};

// run/resume task

task.pendingException = rt.pendingException;
rt.pendingException = {};
rt.currentTask = nullptr;
```

In the first implementation, most exceptions will either be caught immediately
or kill the current task before persisting. Keeping the field on `ThreadTask`
makes the model correct when exceptions and cooperative yield interact later.

## Throw Representation

Throwing means setting `rt.pendingException` to a Java object reference.

Sources:

- `athrow` bytecode.
- VM helper throws such as null checks, array bounds, invalid casts later.
- Native method failure, via `NativeCallResult` or a runtime helper.

Do not use `throw` / `catch` in C++ for Java exceptions. We already measured
large C++ unwind cost in the scheduler path; exception handling must not repeat
that mistake.

## Handler Lookup

On throw, search only the current method frame:

```cpp
bool tryHandlePendingException(Runtime& rt, RuntimeFrame& frame, uint32_t throwPc) {
    for (const auto& h : frame.method->exceptionHandlers) {
        if (throwPc < h.startPc || throwPc >= h.endPc) continue;
        if (h.catchType != 0 && !isInstanceOf(rt, rt.pendingException, h.catchClass)) continue;

        frame.frame.clearStack();
        frame.frame.push(rt.pendingException);
        frame.pc = h.handlerPc;
        rt.pendingException = {};
        return true;
    }
    return false;
}
```

`catchType == 0` is catch-all and is required for `finally`.

Type matching should reuse existing class hierarchy helpers:

- exact exception class match
- superclass match, e.g. `catch (Exception)` catches `EOFException`
- `catch (Throwable)` catches all Java throwable objects

If a thrown value is not an object reference, convert it to a
`NullPointerException`/VM error or treat it as an uncaught VM fault. Java
bytecode should normally only `athrow` `Throwable` references.

## Propagation

When a frame cannot handle the pending exception:

1. Pop the frame.
2. Return to caller with `rt.pendingException` still set.
3. Caller checks handlers for the call-site pc.
4. Repeat until caught or the task stack is empty.

Important detail: the handler range uses the pc of the instruction that threw,
or the call-site pc when a callee returns with `pendingException`.

Natural exception check points:

- after `athrow`
- after `executeMethod(...)` returns to an invoke bytecode
- after native call returns
- after VM helper calls that can throw

Do not add a blanket pending-exception check after every opcode. Keep checks at
opcodes/helpers that can actually create or propagate an exception.

## Uncaught Exceptions

If `pendingException` reaches the top of a straight-line `main` run:

- record an uncaught exception in `ExecutionTrace`
- clear `rt.pendingException`
- stop execution

If it reaches the top of a `ThreadTask`:

- record an uncaught thread exception in `ExecutionTrace`
- mark that task `finished = true`
- clear `task.pendingException`
- release its suspended frame / call stack ownership
- continue running other tasks

The MIDlet/main startup path can initially behave like straight-line execution:
record the uncaught exception and stop that start call. We can decide later
whether an uncaught start exception should terminate the whole app controller.

## ExecutionTrace Additions

Add compact trace records for tests and debugging:

```cpp
struct UncaughtExceptionTrace {
    std::string threadLabel;     // "main", "task:<method label>", etc.
    std::string exceptionClass;  // java/lang/RuntimeException
    std::string methodLabel;     // top frame where it escaped
    uint32_t pc = 0;
};

struct ThreadDeathTrace {
    std::string methodLabel;
    std::string reason;          // "uncaught-exception"
    std::string exceptionClass;
};
```

Store them in `ExecutionTrace`:

```cpp
std::vector<UncaughtExceptionTrace> uncaughtExceptions;
std::vector<ThreadDeathTrace> threadDeaths;
```

Keep this trace-only; do not log synchronously from the interpreter hot path.
Host/controller logging can decide when to print these.

    private String message;

    public Throwable(String message) { this.message = message; }
    public String getMessage() { return message; }
    public String toString() { return message == null ? "" : message; }

No stack trace fields or arrays.

## Native Method Shape

Extend native results without C++ exceptions:

```cpp
struct NativeCallResult {
    bool handled = false;
    std::optional<Value> returnValue;
    std::optional<Value> exception;
};
```

Interpreter native-call sites:

```cpp
NativeCallResult result = handleNative...();
if (result.exception.has_value()) {
    rt.pendingException = *result.exception;
    // route through current frame handler lookup
}
```

Add helpers:

```cpp
Value allocateException(Runtime& rt, const std::string& className);
Value allocateException(Runtime& rt, const std::string& className, const std::string& message);
```

The helper should allocate only the exception object and optional message string.

## Performance Considerations

Happy path:

- no C++ unwind
- no stack trace allocation
- no per-opcode exception check
- no handler lookup unless an exception is pending
- no logging while unwinding

Throw path:

- allocate exception object
- scan current method handler table
- pop frames until a handler is found

This makes exceptions expensive only when thrown. That is acceptable and matches
the intended Java usage: exceptional paths can cost, frame rendering cannot.

Handler lookup stays linear at first because exception tables are tiny. If a real
game shows many throws through methods with large tables, add a per-method cache
or sorted index later.

## Implementation Steps

1. Parse exception tables in `class_file.cpp`.
2. Add throwable boot classes.
3. Add `Runtime` / `ThreadTask` pending exception state.
4. Implement exception object allocation helpers.
5. Implement `athrow`.
6. Implement current-frame handler lookup, including catch-all and superclass
   matching.
7. Wire propagation through invoke/native return paths.
8. Handle uncaught exceptions in straight-line execution and task scheduler.
9. Add trace records for uncaught exceptions and thread death.
10. Add tests.
